# Project Sanctuary - EFP AI Concierge (`backend/ai_agent/`)

An isolated FastAPI microservice that hosts the LangGraph-based AI concierge
agent for the Eternal Fusion Pavilion. It runs in its **own process** on port
`8000`, separate from the synchronous Flask reservation API on port `5000`.

The agent is autonomous, context-aware, long-memory, and human-sounding. It
answers guest questions about the menu, founders, locations, and policies via
RAG; checks availability and makes reservations by calling the Flask API via
tools; signs guests up for the newsletter directly from chat; remembers
guest preferences across sessions; and escalates to a human when a request
exceeds its authority (party size > 12, cancellations, complaints, etc.).

## Why a separate service?

LLM calls are slow (1-30s) and I/O-bound. Running them inside Flask's
Gunicorn worker pool would block the restaurant's transactional reservation
system. The agent service keeps its own async-friendly runtime while sharing
the same Postgres database as the Flask app.

## Architecture guardrails

1. **Process boundary** — This service does NOT run inside the Flask app. It
   runs as a separate FastAPI process on port 8000.
2. **Independent DB engine** — Uses its own `SQLAlchemy` `engine` +
   `sessionmaker` pointing at the same Postgres DB. It does NOT import the
   Flask `db` object from `backend/database.py`.
3. **Single source of truth for schema** — AI tables (`efp_knowledge_chunks`,
   `chat_threads`, `guest_ai_memory`) are created via `init_db.sql` in the repo
   root, not via `Base.metadata.create_all()`.
4. **Streaming-first** — All guest-facing endpoints use SSE (`sse-starlette`)
   so tokens stream to the React frontend as they are generated.
5. **Identity handoff** — Requests forward a `guest_identifier` (a stable
   anonymous browser UUID generated by the frontend; never personal data) into
   LangGraph state. A per-conversation `thread_id` (also a UUID) is persisted in
   browser sessionStorage for multi-turn continuity, so it resets with the tab.
   The guest id stays in localStorage and therefore persists across visits.
6. **Tools wrap the Flask API; they never bypass it.** The agent's reservation
   tools call the existing `/api/reservations/*` endpoints over HTTP. The
   business rules (capacity validation, block checking, room assignment) live
   in one place: the Flask app.
7. **The agent never writes to core tables directly.** AI-specific state
   gets its own tables. The reservation/customer tables are the Flask app's
   territory.
8. **Escalation triggers map to EFP rules.** Party size > 12, soft-block
   override requests, sentiment-detected complaints, and anything touching
   refunds or payments trigger a handoff to a human.
9. **Secrets stay in `.env`** (`OLLAMA_CLOUD_API_KEY`). Nothing sensitive
   ever lands in the repo.

## Tech stack

| Component | Technology |
| :--- | :--- |
| Service runtime | FastAPI + uvicorn (port 8000) |
| Chat LLM | Ollama Cloud `glm-5.3-flash:cloud` |
| Embeddings | Local Ollama `qwen3-embedding:0.6b` (1024-dim, no API key) |
| Vector store | pgvector in the existing Postgres database |
| Agent orchestration | LangGraph 1.x StateGraph with typed state |
| Streaming | Server-Sent Events via `sse-starlette` |
| Database | PostgreSQL 18 + pgvector 0.8.6 (independent SQLAlchemy engine) |
| Tracing | Lightweight local JSON-line tracer (no external dependency) |
| Tests | pytest (169 tests: phases, thread continuity, checkpointer, summarization, chat fixes) |

## Prerequisites

- Python 3.14+
- PostgreSQL 18 with pgvector installed (see
  `docs/pgvector-installation-guide.md` for from-scratch Windows setup)
- Local Ollama running on `http://localhost:11434` with
  `qwen3-embedding:0.6b` pulled:
  ```
  ollama pull qwen3-embedding:0.6b
  ```
- The EFP database initialized via `init_db.sql` at the repo root
- A `.env` file in `backend/` (shared with the Flask app) defining:
  - `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`
  - `OLLAMA_CLOUD_BASE_URL` (default: `https://ollama.com`)
  - `OLLAMA_CLOUD_API_KEY` (your Ollama Cloud API key)
  - `CHAT_MODEL` (default: `glm-5.3-flash:cloud`)

## Spin up the isolated environment

From the `backend/ai_agent/` directory:

```powershell
# 1. Create a dedicated virtual environment (keeps AI deps out of the Flask venv)
python -m venv venv
.\venv\Scripts\Activate.ps1

# 2. Install isolated dependencies
pip install -r requirements.txt

# 3. Run the agent service (port 8000)
python main.py
```

From the repository root, `npm start` starts the Flask API, this agent and the
frontend together. The command above still runs the agent by itself.


## Ingesting the knowledge base

After setting up the database and pgvector, ingest the EFP knowledge
base (menu, about, policies) into pgvector:

```powershell
cd backend\ai_agent
.\venv\Scripts\Activate.ps1
python -m rag.ingest_knowledge
```

This embeds all 40 documents using local Ollama and stores them in the
`efp_knowledge_chunks` table. Re-run whenever the knowledge file changes
(it is idempotent via upsert).

## LangGraph flow

```
START -> memory_retrieve -> triage -> [in_scope?] -> rag -> summarize -> agent
                                                                |
                                                  [tool_calls?] -> tools -> agent (loop, max 5)
                                                                |
                                                  [escalation?] -> escalation -> response
                                                                |
                                                  [answer] -> response -> memory_store -> END
```

- **memory_retrieve**: fetches guest memories from `guest_ai_memory`, injects
  into context (Phase 4: long-term memory). Resets per-turn output fields.
- **triage**: scope check via keyword overlap against the knowledge base.
  Personal questions from known guests are routed to RAG even if keywords
  don't match (memory-aware override).
- **rag**: retrieves top-k context from pgvector, injects guest memories.
  On a follow-up it also retrieves for the previous question joined with the
  current one, then merges both lists by chunk id (higher score wins) and
  keeps `rag_top_k`. Logs the retrieved chunk names at INFO.
  On continuation turns (same `thread_id`), appends the guest's plain
  question to the checkpointed conversation history instead of replacing it.
  Injects the current date so the LLM uses the correct year.
- **summarize**: when the history holds more than 16 conversation messages
  (8 exchanges), compresses older messages into a concise LLM-generated
  summary injected into the system prompt. Only guest `user` messages and
  `assistant` messages with text and no tool calls count; system messages,
  tool results and assistant tool-call messages do not. The last 6
  conversation messages (3 exchanges) stay verbatim with their tool messages.
  Prevents unbounded context window growth (see below).
- **agent**: calls LLM with tools; decides next step (tool call or answer).
  Context for the current request is attached to the latest user message on
  every call, including iterations of the tool loop.
- **tools**: executes tool calls via Flask API HTTP wrappers. Uses
  LangGraph `interrupt()` to hard-gate `create_reservation` behind explicit
  human confirmation (HITL). The graph pauses and resumes via `/api/ai/resume`.
- **escalation**: HITL interrupt for > 12 party size, block overrides, etc.
- **response**: formats the final answer and appends the assistant reply to
  the conversation history (except on the out-of-scope path).
- **memory_store**: skips turns with nothing personal in the guest's message
  (no name, diet, allergy, occasion, contact detail, or history reference)
  unless a `create_reservation` call succeeded. Otherwise it queues fact
  extraction on a background worker and returns immediately; the guest's
  answer is not held back by memory work.

## Multi-turn conversation continuity

The agent supports multi-turn conversations via `thread_id`. The frontend
generates one UUID per conversation (stored in `sessionStorage` as
`efp_thread_id`) and sends it with every message. SessionStorage matches the
visible message cache: closing the tab resets both, while the guest id in
localStorage keeps long-term memory across visits. The "New conversation"
button clears the messages and starts a fresh thread.

The graph's Postgres-backed checkpointer (`PostgresSaver`, with `MemorySaver`
fallback) preserves the conversation state across turns within the same
thread, and `rag_node` appends new turns to the checkpointed history instead
of replacing it.

When `thread_id` is absent, a one-shot `thread_id` is generated and the
agent treats each request as a fresh conversation (backward-compatible).

## Conversation history, summarization and memory

The checkpointed history stores the guest's plain question and the
assistant's answer. Retrieval context (today's date, RAG chunks, guest
memories) is rebuilt for each request and attached only to the copy of the
latest user message sent to the model. Old context blocks are never written
into the history, so prompts stay small and the summarizer sees real dialogue
instead of repeated boilerplate.

Summarization counts only conversation messages: guest `user` messages and
`assistant` messages that have text and no tool calls. System messages, tool
results and assistant tool-call messages are ignored, because they add
prompt size without adding an exchange; counting them made tool-heavy turns
reach the old limit after a few questions. The node runs when the history
holds more than 16 conversation messages (8 exchanges). It keeps the last 6
conversation messages (3 exchanges) verbatim, together with every tool and
tool-call message that sits between them, and moves the cut to a `user`
message so the recent window is a usable turn. Older messages are summarized
into one paragraph. Tool results appear as one short line in the summarizer
transcript. Any previous summary block is removed from the system prompt
before the new summary is appended, so summaries do not stack.

For follow-ups, retrieval runs twice: once for the current question and once
for the previous guest question joined with the current one. This keeps
pronouns and phrases like "which of those" anchored to the earlier topic
(for example, desserts) even though only the latest message is embedded.
The two result lists are merged by chunk id (the higher score survives),
sorted by score, and capped at `rag_top_k`. The second retrieval uses local
embeddings, so it adds no LLM call.

Memory extraction runs after the reply on a single background worker
(`ThreadPoolExecutor(max_workers=1)`). `memory_store` submits plain values
(guest id and transcript), returns immediately, and logs failures without
raising into the graph. A turn is skipped entirely when the guest's message
has no personal indicator and no `create_reservation` call succeeded, so
ordinary menu, story, location and hours questions do not pay for an
extraction call. The extractor is prompted to store only short facts the
guest stated about themselves; it must not turn a question, inquiry or
booking attempt into a preference, and it stores a booking only when the
turn contains a successful `create_reservation` result. Before storing, the
extractor loads the guest's existing facts, includes them in the prompt as
"Facts already known (do not repeat these)", skips normalized duplicates,
and skips facts whose embedding similarity to an existing memory is at or
above 0.92. Each fact is embedded once and the same vector is used for the
duplicate search and the insert. Extraction uses
`MEMORY_EXTRACTION_TIMEOUT` (default 90 s) with no retry; a timed-out call
is logged and the facts for that turn are dropped. Tests and the eval runner
can call `wait_for_memory_jobs(timeout)` to wait for queued jobs.

Under `npm start` on Windows, Ctrl+C stops the services with a forced kill.
A queued extraction job can be lost, which costs at most the facts from the
last turn. Start the agent directly if you need to let memory work finish
before stopping it.

The SSE `stored_memories` frame was removed with the background change; the
frontend never used it. The `memory_store` node frame is still emitted.

## Known limitations

### Booking confirmation uses a hard HITL interrupt

The agent uses LangGraph's `interrupt()` to pause the graph before
executing `create_reservation`. The frontend receives a confirmation card
with the reservation details and Confirm/Cancel buttons. The graph resumes
via `POST /api/ai/resume` only after the user explicitly confirms. This
is a true human-in-the-loop gate, not a prompt-enforced request.

### Graph endpoint does not token-stream

The `/api/ai/graph/stream` endpoint emits the final answer as a single
`{"token": final_answer}` frame, not incremental token-by-token streaming.
This is because LangGraph's `stream_mode="updates"` provides node-level
updates, not token-level. The Phase 1 `/api/ai/chat/stream` endpoint does
real token streaming. Enhancing the graph endpoint to stream tokens
incrementally is future work (requires forwarding the LLM's token stream
through the graph via custom event handlers).

### "Forget me" is not implemented

Guests cannot currently clear their stored memories. A "forget me"
action that deletes all `guest_ai_memory` rows for a `guest_identifier`
is future work.
